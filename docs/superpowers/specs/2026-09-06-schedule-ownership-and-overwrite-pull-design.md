# 乖乖日程归属迁移与覆盖拉取设计

## 背景

日程数据仓库为 `/Users/mac/project/love_diary`。当前仓库已在 `1e3024ff` 删除 353 个重复的无前导零乖乖路径，但仍有 20 个唯一的无前导零乖乖文件待处理：2026-01-14 至 2026-01-31、2026-06-21、2026-07-06。

用户已确认当前连接的 Google Calendar 主账号就是乖乖账号。指定日期范围内读取到 96 个事件，分布在 16 个日期；2026-01-14、2026-01-25、2026-06-21、2026-07-06 没有事件。95 个事件带有 `Created by TimeManager` 描述，另有一个 2026-01-20 20:30–22:00 的「毕设」事件没有该标记。

对照结果表明：20 个旧乖乖文件都包含当前晶晶分类 ID；乖乖与晶晶文件只有 5 天完全相同，其余 15 天存在标签冲突。因此旧乖乖文件不能作为迁移源，晶晶文件不参与写入。

## 目标与边界

- 只修复指定的 20 个乖乖日期。
- Google Calendar 主账号中的事件作为乖乖事件的时间和标题来源。
- 只写入 `schedule/g/YYYY-MM-DD.json`，不再产生无前导零的乖乖路径。
- 不修改任何 `schedule/j` 文件、非目标日期文件或 Google Calendar 事件。
- 新增手机和 Windows 都可用的「覆盖拉取」；覆盖拉取以远端当前身份的补零路径为完整快照，不与本地旧数据合并。
- 在用户确认两部手机更新并成功执行一次覆盖拉取前，不推送远端仓库。

## 数据迁移

### 转换规则

每个 Google Calendar 事件按应用现有的 144 个十分钟槽位转换：开始时间向下取整到槽位，结束时间向上取整；跨日事件按当天范围裁剪。标题写入 `l`，分类颜色写入 `c`，分类 ID 写入 `cid`，并为整批迁移使用统一的迁移时间戳写入文件 `updated_at` 和槽位 `ts`。

迁移结果使用标准对象格式：

```json
{
  "updated_at": 1700000000000,
  "slots": [{"i": 0, "l": "事件标题", "c": 0, "cid": "乖乖分类ID", "ts": 1700000000000}]
}
```

上面的时间戳仅为格式示例；实际迁移时使用同一个真实迁移时间戳。

事件作为乖乖的个人日程写入，不写 `fc` 或 `eid`，避免被软件当作外部 Google 导入而跳过 Gitee/Google 上传。

已知标题只使用 `categories/g.json` 中的分类 ID：

- 学习：多邻国、leetcode、日语。
- 生活：吃饭、健身、洗澡、洗袜子、睡觉、洗衣服。
- 幸福：去北理、回北航、做 app、幸福。
- 休闲：游戏。
- 毕设：毕设。

「开会」在乖乖分类中有多个可能父分类；「写情书」、做被试、什刹海、打扫、休息、去沙河、紫竹院公园等标题没有当前乖乖分类的唯一映射。这些事件的时间和标题已由乖乖日历确认，但语义分类不能确定，统一使用乖乖的「临时」分类，不借用晶晶分类。

### 路径处理

- 16 个有 Google Calendar 事件的日期生成补零后的乖乖 JSON 文件。
- 4 个无事件日期不保留旧内容：删除其无前导零乖乖文件，不创建空日程文件。
- 迁移完成后删除全部 20 个目标无前导零乖乖文件；晶晶的 20 个补零文件保持原样。

### 数据验收

迁移提交前必须验证：

1. 所有新 JSON 都能解析，槽位索引在 0–143 且单日无重复。
2. 每个 `cid` 都来自 `categories/g.json`，不出现 `categories/j.json` 的 ID。
3. 新乖乖文件不含 `fc`、`eid`，日期路径全部补零。
4. `schedule/j` 文件内容和路径未改变。
5. 20 个目标日期与 Google Calendar 事件逐日可重算、可复核。

## 覆盖拉取

### 公共接口与界面

在 `TimeProvider` 增加公开的 `overwriteAllSchedulesFromGitee()`。现有合并拉取保留，新增「覆盖拉取日程」入口：

- Windows：与身份选择、现有全量拉取和全量推送并列显示。
- 手机：加入账户与数据区域，使用当前登录账号映射出的身份。
- 文案明确说明“以远端补零路径为准、会清空本地旧日程、不合并”。

### 拉取流程

1. 校验当前身份、Token、非远程视图，并获取当前身份的 Gitee 日程路径列表。
2. 只接受严格匹配 `schedule/{g|j}/YYYY-MM-DD.json` 的补零路径；无前导零路径直接忽略。
3. 在内存中逐文件读取并严格校验 JSON、槽位索引、重复索引和支持的字段。任一文件读取或校验失败时，保持本地数据和待同步状态不变，整体返回失败。
4. 所有远端文件成功读取后，构建完整快照并一次性替换 `_dailySlots`；不调用 `mergeScheduleSlots`，不保留本地独有日期或槽位。
5. 覆盖前取消 Gitee 防抖推送和 Google 防抖同步；若已有 Google 同步或其他全量同步正在进行，则不执行覆盖，提示稍后重试。
6. 替换成功后清空 Gitee/Google 待同步日期、待处理 Gitee 日期队列和日期 revision，标记全量槽位保存，写入本地并通知界面。
7. 远端没有任何补零日程文件时，也要成功清空本地日程并持久化空快照。

这样，覆盖拉取之后本地只包含远端当前身份的快照；旧本地日期不会留在待同步队列，也不会被后续自动推送重新上传。

### 身份隔离

每次列表读取、文件读取和状态写入都使用同一个已选身份代码。乖乖只能读写 `schedule/g`，晶晶只能读写 `schedule/j`，不根据另一身份的文件作回退或合并。

## 测试与验证

新增或补充测试覆盖：

1. 补零路径校验会忽略无前导零路径。
2. 覆盖拉取会移除本地独有日期和槽位，并保留远端内容。
3. 空远端快照会清空本地，而不是把旧内容合并回来。
4. 读取或 JSON 校验失败时，本地和待同步状态保持不变。
5. 覆盖成功后所有待同步集合、队列和 revision 均清空，后续不会自动上传旧数据。
6. 手机和 Windows 的设置抽屉都能触发覆盖拉取。

提交前运行 `flutter analyze`、相关 Flutter 测试和完整 `flutter test`；条件允许时构建 Android release 和 Windows release，确认两端编译通过。

## 发布门槛

本地提交分为数据迁移提交和软件实现提交，均不自动推送。软件构建并发布后，由用户在两部手机上更新版本，各执行一次覆盖拉取并核对乖乖日程。只有用户确认两部手机结果正确后，才执行仓库推送；在此之前保留本地提交和远端现状不变。
